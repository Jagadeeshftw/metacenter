Returns `400` when `n` is not a non-negative integer.

## Which source answered

`get-coverage-for-cycle` reads pox-5 several times, so a public node refuses it for every cycle (see [Read limits](/docs/verification/read-limits)). Rather than answer with a column of nulls, this route falls back to the cycle's own `calculate-rewards` events — the same events the contract's figures are reconstructed from — and labels the result <Tag kind="mirrored" />, naming the distributions it summed:

## Why this can differ from the dashboard

Both are right; they answer different questions.

| | This route | The dashboard headline |
|---|---|---|
| Window | One whole reward cycle: every distribution booked to it, summed | The **current** cycle, realised so far |
| Source | The cycle's `calculate-rewards` events | `pox5-reader`, through `coverage-cache` |
| Label | <Tag kind="mirrored" /> | <Tag kind="onchain" /> |

So a finished cycle and the cycle in progress will not match, and should not. Even for the same window, the contract rebuilds the pool from rewards-per-token × shares, which can land within a couple of sats of the event total through integer truncation; `npm run verify` allows exactly that tolerance and no more.
